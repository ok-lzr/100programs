# 017 · CSV 与 JSON 互转工具

> ★½☆☆☆　难度 1.5 / 5　·　001–020 · 找回手感
> 3 ~ 4 小时，分 4 次　·　1 个文件（csv_json.py），约 170 行　·　只用 Python 自带功能（csv 和 json 都是自带的）
>
> **规矩：这份任务卡只给思路和语法点，一行代码都没有。代码由你自己写。**

**一句话**：表格文件和 JSON 互相转换，还能自动认编码和分隔符

## 为什么做它

你以后会遇到的所有数据几乎都是这两种格式之一：表格软件导出的是 CSV，程序之间传数据用的是 JSON。能随手把它们互转，是「会用电脑处理数据」和「只会用鼠标点」的分水岭。而且这个项目会第一次让你面对真实的脏数据——编码不对、分隔符不对、空行缺列，全都得处理。

## 做完是什么样

程序有三种功能：把 CSV 转成 JSON、把 JSON 转成 CSV、把 CSV 打印成好看的表格看前几行。它自己会判断文件用的是逗号还是制表符、是 UTF-8 还是 GBK；遇到坏行会跳过并告诉你跳了几行。约 170 行，一个文件。

## 会练到的语法

`import csv`　`import json`　`读表头`　`字典推导`　`写入 JSON 时保中文`　`列表推导`　`编码尝试`　`分隔符判断`　`跳过坏行并统计`　`逐行处理大文件`

> 新东西是「两套数据结构之间的映射」：表格的行列怎么变成字典，字典怎么变回表格——这是所有数据处理的基本功。

## 关卡 1 · 先把 CSV 读进来

**建议用时**：25 分钟

### 做出这样就算过

自己造一个 CSV 文件（用记事本就能写：第一行是表头，后面几行数据，中间用逗号隔开），程序读出来并打印每一行，行与行之间用竖线分隔，方便看清列。最后打印「共 5 行，4 列」。

### 怎么想（步骤）

1. 新建 csv_json.py，用记事本手写一个小 CSV：表头写「姓名,科目,分数」，下面写几行数据，故意留一行只有三个字段里的两个
2. 用自带的功能读这个文件：它会把每一行切成一个列表，自动处理逗号
3. 逐行打印，把列表里的每一项用竖线连起来，这样列的错位一眼就能看出来
4. 统计行数和列数（列数取表头那一行的长度）
5. 把带缺失字段的那一行也打印出来看看，观察它比别的行短——这一关先不修它

### 要用到的语法点

- **import csv**：自带模块，专门处理这种用分隔符隔开的表格文件
- **读文件并按行切开**：给它一个打开的文件，它会一行行给你列表，连引号里的逗号都能正确处理
- **打开文件时指定编码**：不指定编码时，中文可能读成乱码，这一步别偷懒
- **连接列表里的项**：用竖线把一行里的几列连起来打印，比直接打印列表好看很多
- **数行数**：边读边记一个计数器，或者先把所有行读进列表再数长度

### 做完了自己检查

- [ ] 每一行的列都用竖线分开了，能看出列的边界
- [ ] 表头是单独一行，没有被当成数据
- [ ] 缺字段的那一行明显比别的短
- [ ] 文件不存在时给提示不崩
- [ ] 中文没有乱码

### 卡住看这里

- 中文变成乱码：打开文件时没指定编码，或者文件本身不是 UTF-8（下一关会解决）
- 每行之间多了一个空行：CSV 文件每行结尾本来就带换行，打印时又加了一次，去掉一个就行
- 所有内容挤成一行：读取时没用按行切分的方式，而是把整个文件当字符串读了

### 常见坑

- 用逗号自己切分字符串（如果某个字段里有逗号，切出来就错位了；用专门的模块没这个问题）
- 以为 CSV 一定是逗号分隔的（还有分号、制表符，下一关要自动判断）

## 关卡 2 · CSV 转成 JSON

**建议用时**：35 分钟

### 做出这样就算过

程序把 CSV 变成 JSON：表头当键、每一行当一个字典，全部存成一个列表写进 json 文件。生成的文件用记事本打开能看到中文（不是一串编码）、并且有缩进方便看。原 CSV 里的缺失字段在 JSON 里显示成空文字。

### 怎么想（步骤）

1. 先把 CSV 整个读进来，把第一行当表头，剩下的当数据行
2. 每一行都用表头和值配对，组装成一个字典。数据行比表头短的时候，用空文字补齐，保证每行的键一样多
3. 把所有字典收进一个列表
4. 把这个列表写成 JSON 文件：要开启缩进让文件好看，同时关掉「把中文转成编码」的选项，否则中文会变成一串看不懂的符号
5. 写完之后再把 JSON 读回来打印一下，验证写对了

### 要用到的语法点

- **表头与数据分开**：读出来的第一行单独存成表头，剩下的才是数据
- **字典配对**：把表头和数据用配对的方式组装成字典；表头里的名字就成了键
- **列表推导或循环组装**：每一行都做一次同样的组装，可以用循环也可以用更短的写法
- **写 JSON 的缩进参数**：缩进参数给一个数字（比如 2），文件就会分行缩进，人看得懂
- **关掉中文转义**：默认会把中文写成编码形式，关掉这个选项中文才是中文

### 做完了自己检查

- [ ] 生成的 JSON 文件里每一行数据都是一个带键的字典
- [ ] 中文在文件里能直接看懂，不是一串斜杠字母
- [ ] 缺字段的那一行里，缺的键在，值是空文字
- [ ] 把 JSON 重新读回来打印，内容跟 CSV 对得上
- [ ] 换了行顺序读，键的顺序不影响内容（JSON 里字典的键顺序不重要）

### 卡住看这里

- 报错说键的数量不对：某一行比表头短或长，组装前先按表头长度补齐或截断
- 中文变成乱码：写入时忘了关掉中文转义，或者忘了指定编码
- 文件全挤在一行：缩进参数没给

### 常见坑

- 直接把每一行当列表写进 JSON（那样就丢了「哪一列是什么」的信息，等于白转）
- 用表头当键时忘了去掉表头里可能存在的空格

## 关卡 3 · 再转回去：JSON 变 CSV

**建议用时**：35 分钟

### 做出这样就算过

程序读一个 JSON 列表文件，写出对应的 CSV：所有出现过的键合成表头，每一行按表头顺序填值，缺的填空。转出来的 CSV 用表格软件或记事本打开，能直接看懂。

### 怎么想（步骤）

1. 读 JSON 文件，得到一个列表（每一项是字典）。先检查一下：它是不是一个列表？里面每一项是不是字典？不是就给提示
2. 收集表头：把所有字典的键合起来去重。用集合收集再排序，顺序就固定了，每次运行结果一样
3. 写 CSV：先写表头，再逐行按表头顺序取值。某个字典里没有这个键时填空文字
4. 写的时候用专门的功能写，它会自动处理「字段里有逗号」这种情况（会给字段加引号）
5. 转完再读回来看一眼，或者直接用表格软件打开检查

### 要用到的语法点

- **集合收集所有键**：遍历每个字典，把键丢进集合，自动去重
- **排序固定顺序**：集合本身没有顺序，排一下序，保证每次生成的表头一样
- **按顺序取值**：用字典的取值方法配上默认值，缺字段时给空文字而不是报错
- **写 CSV**：有专门的写入功能，它会帮你处理字段里的逗号和引号
- **类型检查**：处理之前先确认数据长什么样，不是预期结构就明确报错，别硬着头皮转

### 做完了自己检查

- [ ] 生成的 CSV 第一行是表头，顺序跟上一关的 JSON 键一致
- [ ] 缺字段的行在该列是空的，没有错位
- [ ] 字段里带逗号的内容被正确包了起来（自己造一条测试）
- [ ] JSON 文件不是一个列表时给出清楚提示
- [ ] 来回转一圈（CSV 到 JSON 再到 CSV）内容不丢

### 卡住看这里

- 转出来的 CSV 列错位：写的时候没按表头顺序取，或者用了字符串拼接而不是专门的写入功能
- 表头每次都变：没排序（集合的顺序不固定）
- 报错说不能下标取值：JSON 顶层不是列表，而是个字典，先确认文件结构

### 常见坑

- 自己用逗号拼字符串写 CSV（字段里有逗号就会毁掉整个文件）
- 把数字和文字混着写进去，表格软件里数字变成了文本（这一关可以先不管，知道有这回事就行）

## 关卡 4 · 对付真实世界的脏数据

**建议用时**：35 分钟

### 做出这样就算过

程序能自动处理三种常见问题：文件是 GBK 编码时也能读（提示「已按 GBK 读取」）、分隔符是制表符时也能认（提示「检测到制表符分隔」）、坏行（字段数不对或整行空白）自动跳过并汇报「跳过 2 行」。全部处理完打印一份小报告。

### 怎么想（步骤）

1. 编码探测：先用 UTF-8 试着读；读失败就换 GBK 再试；都失败就提示用户。把最终用的编码记下来
2. 分隔符判断：读前几行，数一数逗号和制表符哪个出现得多，就用哪个
3. 坏行处理：字段数与表头不一致的行记进一个名单（带上行号），不参与转换
4. 处理完打印报告：用的什么编码、什么分隔符、成功几行、跳过几行（列出前三个跳过的行号）
5. 想清楚大文件怎么办：不要一次把整个文件读进内存，改成读一行处理一行写一行——顺便在报告里说明你用的是哪种方式

### 要用到的语法点

- **异常尝试**：用 try / except 把「换一种编码再试」串起来，注意两次尝试要分别接住异常
- **字符串计数**：数某个符号在字符串里出现几次，有现成方法
- **逐行读取**：打开的文件本身就可以一行行遍历，不必先读成一个大字符串
- **带行号的收集**：跳过坏行时顺手记下行号，汇报时更有用
- **报告组装**：把要汇报的几行先攒成列表，最后统一打印

### 做完了自己检查

- [ ] GBK 编码的 CSV 能正确读出中文，并提示用了 GBK
- [ ] 制表符分隔的文件被自动识别，没有被当成只有一列
- [ ] 坏行被跳过且报告里有数量和前几个行号
- [ ] 全是坏行时程序不崩，输出「没有可转换的数据」
- [ ] 处理一个几万行的文件时内存没有明显上涨（说明是逐行处理的）

### 卡住看这里

- GBK 也读不出来：有的文件是 GB18030，再加一种尝试；另外别把「文件不存在」和「编码不对」混成一个提示
- 制表符判断反了：数的时候把表头也算进去更准
- 坏行太多：先打印前几行原始内容看看分隔符到底对不对

### 常见坑

- 把异常处理写成「出了任何错都返回空」，结果真正的 bug 也看不见了
- 跳过坏行却不记录，最后数据少了也不知道少在哪
